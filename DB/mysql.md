### 命名规范

#### 1.1 基本命名规则：

1. 只能使用英文字母，数字，下划线，并以英文字母开头，词汇中间以下划线分隔

2. 库，表，字段全部采用小写，不要使用驼峰式命名

3. 尽量避免使用 `MYSQL` 保留字段，如 `desc` , `index`，`order` 等

4. 命名禁止超过 32 个字符，须见名知意

5. 数据库命名必须为项目英文名称或有意义的缩写

### 设计规范

1. 如无特殊需求，存储引擎使用 `InnoDB`

    ```json
    InnoDB 优点：
    1. 支持事务
    2. 支持行级锁
    3. 并发性能好

    ps：补充知识 MyISAM 存储引擎
    1. 不支持事务
    2. 不支持外键
    3. 非聚集索引
    4. 只支持表级锁

    ```

2. 数据库和表的字符集统一使用 `utf8` 或者 `utf8mb4`

    ```json
    无特殊情况，使用版本默认即可
    8.0 版本之前，默认字符集为 utf8
    8.0 版本之后，默认字符集为 utf8mb4
    5.5.3 版本之后增加了 utf8mb4 字符编码，但是没有支持为默认编码
    普通的 utf8 编码长度为 3 字节， uft8mb4 长度为 4 字节，支持 Emoji表情
    ```

3. `InnoDB` 字符集默认排序使用 `_general_ci` 和 `_unicode_ci`， 推荐使用 `_general_ci`

    ```sql
    示例：
    `sender_id` varchar(255) CHARACTER SET utf8 COLLATE utf8_general_ci NOT NULL COMMENT '发送者'

    ci 不区分大小写
    cx 区分大小写
    general 速度更快，准确性稍低
    ```

4. 数据库表和字段都需要添加备注，以便更好的理解建表思路

    ```sql
    字段备注：
    `chain` varchar(20) NOT NULL DEFAULT '' COMMENT '钱包归属链',

    表备注：
    DEFAULT CHARSET=utf8 COMMENT='钱包API访问统计表';
    ```

5. 单表设计存储应少于 500 万条 或 单表容量不超过 2G

    ```json
    mysql 数据库设计问题，经业内公司大量测试，数据量超过一定阈值，或容量达到阈值后，检索能力会大幅度下降
    ```

6. 单表列数目必须小于 30，若超过则应该考虑分表

    ```json
    单表列数太多，会使得 Mysql 处理 InnoDB 返回数据之间的映射成本太高
    ```

7. 表必备字段，`id` , `created_time`

    ```json
    id: unsigned bigint  主键自增ID ，必备的原因和 Mysql 的 B+Tree 数据结构有关，更利于索引检索
    created_time：datetime 创建时间
    ```

8. 表字段必须定义为 `NOT NULL` 并且提供默认值

    ```json
    NULL 需要更多的存储空间，无论是表还是索引中每行 NULL 的列都需要额外的空间来标识。
    NULL 类型需要 Mysql 内部进行特殊处理，增加了数据库处理记录的复杂性。
    ```

9. 小数类型为` decimal` ，静止使用 `float `和 `double`

    ```
    float 和 double 在存储过程中，存在精度损失的问题
    ```

10. 不建议使用，存储过程、触发器，外键 等额外功能

    ```json
    存储过程：过度复杂的逻辑容易造成死锁，可以替换为后端业务实现
    触发器：高并发情况下不理想，可以用事务代替
    外键：导致表与表之间的耦合，十分影响SQL性能，甚至会造成死锁
    ```

11. 时间类型 不要使用 `varchar` 或` int` 等

    ```json
    使用 datetime，占用8字节，明确日期时间
    使用timestamp，占用4字节，查询比int快，但是有使用限制，不建议使用
    timestamp 取值范围: 1970-01-01  ~ 2038-01-19
    ```

### 索引规范

1. 业务上具体唯一特性的字段，即使是多个字段的组合，也建议建成唯一索引

    ```json
    业务上的唯一索引，并不会影响到 insert 语句是耗时，不仅避免了脏数据的出现，也提高了查询速度
    ```

2. 单表索引不宜超过 5 个，如果需要增加的索引过多，建议在业务层面上进行重构拆分

3. 频繁更新的列，不建议有索引

4. 介绍一些索引失效的情况：

    ```sql
    1. where 条件中使用 or
    	a. or 连接的字段若有非索引字段，则索引失效
    	b. or 连接的字段若是两个不同索引字段或者同一个索引的不同字段，则索引失效（可以使用 UNION 代替 OR）
    	c. or 连接的字段若是两个相同索引的索引字段，则索引生效（可以用 IN 代替 OR）

    2. where 条件中使用 like
    	a. like 的值中带 % 或者 _ 的前缀匹配符，则索引失效
    		where phone like '%123456789'
    	b. like 的值中带 % 或者 _ 的通配符，但不置于其前缀，则索引生效
    		where phone like '123456789%'

    3. where 条件中使用了组合索引，但没有遵循最左前缀原则，则索引失效

    4. where 条件中对索引列使用了函数，则索引失效
    	where ABS('username') = 'root'
    	where TRIM('username') = 'root'

    5. where 条件中对索引列使用数据运算，则索引失效
    	where id = id/2
    	但是改为 id = a/2 则索引生效（字段本身不参与运算）
    	where id = 43434343/2

    6. where 条件中存在索引列的数据类型的隐式转换
    	phone 字段为 varchar 类型
    	where phone = 1234567

    7. where 条件中存在 NULL

    ```
